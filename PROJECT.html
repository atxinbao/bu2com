BU2.COM · PROJECT ALIGNMENT & FUTURE ROADMAP

项目总纲与监管可演进模型

在 AI Agent 支付法域仍然模糊的阶段，BU2 不等待一个全球统一答案，而是通过可配置的监管状态、有限授权与分层执行模式，在保持技术前进的同时控制真实资金边界。

版本 1.1生效日期 2026-09-06状态 ENV-02 Implemented · R2 review pending维护者 BU2 Engineering / Codex
Frozen project decision
BU2 是 Agent 支付授权、控制、执行编排和证据网络；默认不托管资金，通过非托管钱包或持牌合作方完成真实结算。

一、项目定位

Agent 不是独立法律主体。真实付款责任始终归属于可识别的人或企业，Agent 是通过 Credential 和 PaymentMandate 获得有限权限的软件执行者。

BU2 初始定位
  • 支付意图和授权策略
  • 确定性交易编排
  • Agent 身份与 Mandate
  • Receipt、审计和对账基础设施
  • 支付 Provider 的统一控制层
BU2 初期不是
  • 银行或稳定币发行方
  • 客户资金托管机构
  • 货币兑换商
  • Merchant of Record
  • 可随意代客发起支付的机构

产品界面应区分 Authorized Amount、Provider Balance、Reserved Amount 和 Available Spending Capacity，不把外部 Provider 或链上钱包中的资金描述为“BU2 客户余额”。

二、四种支付执行模式

监管边界不写死在 Transaction Core 中。真实能力通过 ExecutionMode 和有效的监管能力授权逐级开放。

SIMULATED

本地模拟执行

仅用于 local 开发、自动化测试与故障注入；不是对外 Sandbox，也不形成链上支付证据。

Local only
NON_CUSTODIAL

用户控制资金

用户或企业控制钱包/支付账户，BU2 验证 Mandate 和策略，Provider 或 Facilitator 执行，资金直接到商户。

First live
LICENSED_PARTNER

持牌合作方执行

银行卡、银行账户、法币钱包、稳定币托管与出入金由持牌 PSP、银行或托管机构完成。

Partner gated
BU2_CUSTODIAL

BU2 自有托管

仅保留接口和未来数据边界。在牌照、资产隔离、双式账本、合规与运营条件完成前永久禁止启用。

Disabled
用户控制的钱包 / 持牌 Provider ↓ 有限授权 BU2 PaymentMandate ↓ 确定性策略 Transaction Core ↓ Adapter Provider / x402 Facilitator 执行 ↓ 商户收款 + BU2 Receipt + Reconciliation

三、Sandbox / Live 系统环境

对外服务环境只有 sandbox 与 live；内部开发环境为 local。环境、执行后端和资金准入相互独立，不能从 Adapter 名称推导环境，也不能用 live 字符串代替主网付款许可。

Sandbox
  • Base Sepolia · 84532
  • eip155:84532
  • x402 测试资产
  • 托管开放需独立验收
Live
  • Base Mainnet · 8453
  • eip155:8453
  • 初始 execution_disabled
  • G-L 前禁止签名和广播

Sandbox 与 Live 复用同一不可变软件制品，但数据库、API key、Signer、Receipt 信任域、Webhook、队列、存储、备份和运行身份必须隔离。ENV-02 已实现运行时注册表、数据库绑定和链/Signer/Provider 断言；公开 API、SDK、MCP、Doctor 与 Receipt 的 legacy simulation/testnet 由 ENV-03 迁移，旧 Receipt 保留原字段和原签名解释。

local + simulated sandbox + x402 + 84532 live + x402 + 8453 + execution_disabled 任何其他组合 = DENIED

四、法律主体与责任链

系统不允许 AgentIdentity 脱离法律主体成为独立付款人。每笔真实交易必须能够回到一个自然人或法人。

LegalPrincipal (natural_person | legal_entity) ↓ Account ↓ AgentIdentity ↓ Credential ↓ PaymentMandate ↓ PaymentIntent ↓ Provider Execution
01

责任可归属

交易必须保存 legal_principal、account、agent、credential 和 mandate 标识。

02

授权可撤销

Mandate 必须限定金额、商户、用途、资产、环境、有效期和转授权限。

03

职责可证明

必须记录谁持有资金、谁签名、谁 KYC、谁负责争议和最终结算。

五、监管能力注册表

系统不使用简单的“国家允许/禁止”开关，而是根据主体、商户、资产、网络、Provider 和控制能力判断某条执行路径是否获得批准。

RegulatoryProfile
├── principal_jurisdiction
├── merchant_jurisdiction
├── service_entity
├── execution_mode
├── asset + network
├── execution_provider
├── fund_controller
├── signing_controller
├── kyc_owner / aml_owner
├── dispute_owner / reconciliation_owner
├── limits
├── legal_review_id
└── expires_at

每个 Adapter 必须绑定有效的 CapabilityGrant。当“法域 × 主体 × 商户 × 资产 × 网络 × Provider × 服务行为”没有有效授权时：

LIVE EXECUTION = DENIED LOCAL SIMULATION = ALLOWED

监管判断必须有版本和有效期；过期后自动降级为暂停真实执行，而不是继续沿用历史判断。

六、Agent 原生授权模型

模型可以提出支付意图，但不得自行修改金额边界、扩大权限或改变 Mandate。所有资金判断由确定性系统完成。

Principal Mandate → Agent Delegation → Transaction Mandate → Policy Decision → Provider Authorization → Settlement Evidence → BU2 Receipt

Mandate 至少支持：单次/日/月限额、商户白名单、商品类别、环境、有效期、可退款要求、高风险工具限制、子 Agent 转授、一次性 nonce、授权版本和随时撤销。

这与 AP2 的 IntentMandate → PaymentMandate → PaymentReceipt 思路兼容，但 BU2 保留自己的稳定领域对象，不让外部协议重新定义核心交易状态。

七、双层账本事实模型

非托管并不意味着不需要账本。BU2 必须保存自身交易事实和外部资金证据，但不得声称内部记录天然等于真实资金完成。

BU2 交易事实

  • requested / authorized
  • provider_submitted
  • provider_unknown
  • provider_confirmed
  • delivery_verified
  • reconciled / refunded / disputed

外部资金事实

  • provider_transaction_id
  • network_transaction_hash
  • settlement_batch_id
  • bank_statement_reference
  • provider balance evidence
  • settlement finality evidence
Provider Evidence + Settlement Finality + BU2 Reconciliation = reconciled

当前阶段建设双式技术账本和清算账户；只有进入 BU2 Custodial 模式，才增加客户资产总账、资产隔离、会计关账和监管财务报告。

八、未来路线图

Phase 0 · 当前

Local Simulation、隔离 Sandbox、Base Sepolia、PaymentMandate、策略判断、Receipt、持久化账本和自动化测试；Live 仅纳入架构且 execution disabled。

Phase 1 · 受限真实试点

邀请制、用户控制非托管钱包、单一 USDC、单一网络、低限额、商户白名单、每笔可验证 Receipt；禁止提现、换汇、资金归集和跨客户代付。

Phase 2 · 持牌合作方

引入银行卡、银行账户和法币能力；合作方负责客户资金、KYC/KYB、AML 与真实结算，BU2 负责 Agent 授权和支付控制层。

Phase 3 · 牌照评估

只有客户明确要求 BU2 持有余额、统一结算、跨客户调拨或直接出入金时，才启动自有牌照与托管能力评估。

任何产品演示、收入压力或技术可行性都不能自动提升执行模式。能力升级必须由明确的准入证据触发。

十、依据与解释边界

  • 英国 FCA：支付发起服务监管说明——说明不持有账户本身并不自动排除支付发起监管。
  • 美国 FinCEN：虚拟货币业务模型指引——监管判断关注资产所有权、存储、交互路径与中间方控制能力。
  • 香港金管局：储值支付工具许可说明——储存价值并用于第三方支付可能进入许可范围。
  • Google：Agent Payments Protocol——提供 IntentMandate、PaymentMandate 和 PaymentReceipt 的授权审计思路。
  • Coinbase：托管与非托管支付架构、x402 Facilitator——提供用户控制钱包、点对点支付与 Facilitator 边界参考。
  • Base：eth_chainId、Circle：USDC 合约地址——确认 Base Mainnet/Sepolia 的链标识、资产地址与测试资产边界。

本文件是产品和技术边界方案，不构成任何司法辖区的法律意见。具体真实执行路径仍需结合目标市场、业务流程和合作方进行独立法律审查，并形成版本化 CapabilityGrant。
