项目治理制度

建立从需求、决策、实施、验证、发布、运营到退役的完整责任链，让每项能力不仅“能做出来”，还能够被批准、追溯、运营和安全退出。

版本 1.1生效日期 2026-09-06状态 ENV-06 Implemented · R2 review pending维护者 BU2 Engineering / Codex
Governance principle

没有所有者的能力不得上线；没有证据的变更不得完成；没有到期时间的例外不得存在。

一、文档权威层级

项目文件发生冲突时按以下顺序处理，低层文件不得静默覆盖高层决策。

法律与外部约束监管、支付通道、合同和生产运行限制
AGENTS.md所有 AI Agent 的强制行为规则
PROJECT.html项目定位、执行模式和阶段准入门槛
ARCHITECTURE.html长期业务事实与系统不变量
GOVERNANCE.html决策、责任、变更、发布和运营制度
ADR / Contracts具体决策、API、事件、Schema 和迁移
CHANGELOG.html实际变更与验证历史
模块文档与代码实现细节，不得重新定义上层原则

二、项目生命周期

所有工作必须进入明确阶段，不允许从想法直接跳到生产。

01Discover

问题、用户、证据、边界和不做什么。

02Ready

所有者、验收、风险、依赖和恢复方案完整。

03Decide

需要时建立 ADR，明确选择及重新评估条件。

04Implement

按风险等级小步实现并同步 Changelog。

05Verify

测试、契约、迁移、故障恢复和证据审查。

06Release

准入检查、Canary、监控、停止和回滚条件。

07Operate

SLO、对账、告警、案件、事故和容量管理。

08Retire

弃用、迁移、历史验证、数据保留和关闭。

三、责任与批准

项目早期允许同一人承担多个角色，但每个决策必须明确其当时所代表的角色。AI Agent 只能作为 Contributor 或 Verifier，不得独立承担 R2/R3 Approver。

角色主要责任不可替代的批准
Project Owner愿景、范围、商业优先级和资源项目定位与阶段切换
Product Owner用户问题、PRD、验收和发布说明用户行为变化
Transaction Domain Owner状态机、金额、账本、结算和对账金融不变量 R2/R3
Architecture Owner边界、ADR、契约、迁移和长期可替换性架构与数据所有权
Operations OwnerSLO、发布、告警、事故、恢复和容量生产准入与恢复
Compliance/Legal OwnerCapabilityGrant、责任矩阵和法域审查真实执行能力开放
AI Agent分析、实现、测试、证据和文档对齐无；不得自批 R2/R3

四、Definition of Ready / Done

Definition of Ready

  • 目标、非目标和用户价值明确
  • Owner 与风险等级明确
  • 输入、输出、状态和数据所有者明确
  • 金融不变量和兼容影响明确
  • 验收标准与测试策略明确
  • 失败、恢复和 Changelog 计划明确

Definition of Done

  • 实现与批准范围一致
  • 测试、构建和契约验证已运行
  • 迁移、回滚和运营手册可执行
  • 监控、对账与告警覆盖新行为
  • 文档和 CHANGELOG 完全对齐
  • 残余风险、Owner 和到期时间明确

不满足 Ready 不得开工；不满足 Done 不得交付。时间压力只能调整范围，不能降低金融不变量。

五、决策、风险与例外

重大决策、未消除风险和临时例外必须进入独立登记，不允许只存在于聊天、Prompt 或口头共识。

ADR

记录背景、候选方案、选择、后果和重新评估条件。

要求已内置

Decision Register

项目所有有效决定的索引、Owner、状态和替代关系。

要求已内置

Risk Register

概率、影响、控制、残余风险、Owner 和复审日期。

要求已内置

Exception Register

规则例外必须有范围、补偿控制、批准人与自动到期日。

要求已内置

永久例外无效。例外到期时系统必须恢复原规则、获得新批准或停止相关能力。

六、发布与变更制度

发布单位是可观察行为及其证据，不只是代码提交。每次发布必须能回答“改变了什么、风险是什么、如何停止、如何恢复”。

等级最低批准最低证据
R0 文档/展示Owner 或维护者格式、链接、渲染
R1 普通逻辑模块 OwnerLint、类型、单元测试、构建
R2 交易相关Domain + Architecture不变量、集成、并发、恢复、兼容和回滚
R3 真实资金Project Owner 明确批准（受阶段准入门槛约束）Sandbox E2E、Canary、监控、对账、备份和人工执行窗口

环境建设与资金启用是两个决定。Sandbox/Live 配置、部署模板或只读入口可以在对应 R2 审查后建设；Live 必须保持 execution_disabled，直至 G-F、G-L、有效 CapabilityGrant、租户启用和 Mandate 全部满足。PR 合并、环境字符串或单一布尔值均不构成主网执行授权。

七、事故与恢复制度

Detect → Contain → Preserve Evidence → Reconcile → Recover → Communicate → Postmortem → Permanent Regression Test

资金状态未知时，优先停止扩大影响并保留证据，不得通过重复扣款或直接改库“恢复”。事故复盘必须无责但有行动项，每个行动项具备 Owner、期限和验证方式。

八、退役与技术债制度

  • API、事件、Adapter、密钥、策略和数据结构必须具备版本、Owner 与退役条件。
  • 弃用必须经过公告、兼容期、使用量观测、迁移验证和关闭批准。
  • 历史 Receipt、Ledger 和公钥验证能力不得随实现退役而丢失。
  • 技术债必须记录影响、临时控制、Owner 和目标偿还日期；“以后处理”不是有效状态。
  • 能力关闭后必须撤销凭证、停止流量、归档证据、更新 Changelog 并验证无法重新误启。

九、治理节奏

每次变更

Ready、风险分级、测试证据、Changelog 和 Done。

每周

风险、例外、未知交易、死信、依赖和技术债复审。

每月

项目路线、SLO、对账、容量、密钥和 CapabilityGrant 复审。

每季度

灾备恢复、账本重建、Provider 退出和旧版本退役演练。

每次事故

证据保全、对账恢复、复盘和永久回归测试。

每次阶段升级

重新批准 PROJECT.html 中的阶段准入门槛。
