# BU2 协议引入计划 v0.1

## 1. 决策摘要

BU2 不以“支持最多协议”为产品目标，而以“完成可验证、可结算、可追溯的 Agent 收付款”为目标。

协议引入顺序：

```text
P0 内部语义模型
  → P1 x402 沙盒
  → P2 x402 受控生产闭环
  → P3 AP2 适配器
  → P4 多支付通道编排
```

核心判断：

- **x402 解决支付执行问题**：Agent 如何按请求购买 API、数据和数字服务。
- **AP2 解决授权证明问题**：如何证明用户授予了 Agent 特定购买权限，并形成不可抵赖的意图和交易证据。
- **BU2 Policy Engine 解决产品治理问题**：这笔申请在当前组织、项目、Agent 和任务规则下是否允许。

三者互补，但不能互相替代。

## 2. 协议与 BU2 产品层的关系

```text
账户所有者
      ↓
BU2 Agent Identity / Wallet / Payment Mandate
      ↓
BU2 Quote / Payment Intent
      ↓
BU2 Authorization / Funds Reservation
      ↓
Payment Adapter
  ├── x402
  ├── AP2-compatible rail
  ├── Virtual Card
  └── Existing Provider Balance
      ↓
BU2 Transaction + Delivery Evidence + Settlement + Receipt
```

BU2 的核心对象必须独立于任何协议。外部协议只能通过适配器读写这些稳定对象。

## 3. P0：MVP 不接入真实支付协议

### 目标

验证买卖双方 Agent 是否需要嵌入式报价、授权、资金预留、交付结算和机器可读凭证。

### 实现

- 内部 `Agent Identity`：哪个 Agent 代表哪个 Account。
- 内部 `Payment Mandate`：Agent 可以在什么范围内自主支付。
- 内部 `Quote / Payment Intent`：交易双方、商品、金额、用途和有效期。
- 内部 `Authorization`：自动允许、请求确认或拒绝。
- 内部 `Transaction / Settlement / Receipt`：预留、交付、结算与凭证。
- 模拟支付适配器：用于正常、失败、退款和超时测试。

### 明确不做

- 不实现 AP2 Mandate 签名和验证。
- 不连接稳定币主网。
- 不创建托管钱包。
- 不提供提现、兑换或通用转账。
- 不为满足协议示例而增加购物车、电商目录或消费者账户。

### 退出门槛

- 至少 3 家团队完成试点。
- 至少 30 笔交易完成预留、交付、结算和 Receipt 闭环。
- 至少 2 个试点愿意继续接入真实支付通道。
- 策略重放一致率达到 100%。

如果这些条件不成立，不进入真实支付阶段。

## 4. P1：x402 沙盒验证

### 为什么 x402 先进入

x402 的产品闭环较短：Agent 请求一个付费 HTTP 服务，服务返回支付要求，Agent 完成支付后重试并获取结果。它适合验证 BU2 是否能把策略判断、支付执行和交付证据连接起来。

### 范围

- 单一测试网络或沙盒环境。
- 单一稳定币或测试资产。
- 一个 BU2 控制的测试商户。
- 固定小额上限。
- 非托管钱包连接。
- 仅允许预先配置的服务类别。

### 用户故事

> 作为 Agent 开发者，我希望研究 Agent 在 0.10 美元上限内购买一次数据查询，并在 BU2 中看到授权、支付和交付的完整记录。

### 验收标准

- Agent 私钥不进入模型上下文。
- 每次支付必须先获得 BU2 Policy Decision。
- 支付金额不能超过批准金额。
- 支付结果与原始 Spend Request 绑定。
- 商户交付失败时不标记为完成任务。
- 重试不会产生重复支付。

### 禁止扩展线

- 不支持任意链和任意代币。
- 不开放用户自定义收款地址。
- 不做兑换、跨链、收益或资产组合展示。
- 不做通用钱包余额页。
- 不建设商户市场。

## 5. P2：x402 受控生产闭环

### 进入条件

- 沙盒完成不少于 100 次支付测试。
- 重复支付为 0。
- 支付与交付状态能够稳定核对。
- 至少 3 家工具商明确愿意接入。
- 已完成目标地区的合规路径评估。

### 新增范围

- 少量白名单商户。
- 真实小额稳定币支付。
- 商户和服务目录只用于治理配置，不做开放市场。
- 退款、冲正和争议状态。
- 支付通道健康状态和失败切换。

### 产品目标

验证客户是否愿意为“支付编排 + 策略 + 审计”付费，而不是验证代币交易需求。

## 6. P3：AP2 适配器

### 为什么 AP2 后进入

AP2 面向跨 Agent、商户和支付提供商的可信授权，使用可验证的 Intent Mandate 和 Cart Mandate 表达用户意图及具体交易内容。只有当 BU2 已进入真实商业交易、多个商户或多个支付方式后，互操作授权凭证才产生足够价值。

### BU2 映射

| BU2 对象 | AP2 概念 | 映射原则 |
| --- | --- | --- |
| Payment Mandate | Intent Mandate | 表达用户允许 Agent 做什么 |
| Quote / Payment Intent | Cart / transaction context | 表达具体商品、商户和金额 |
| Authorization | BU2 内部授权结果 | 不由 AP2 替代 |
| Human Decision | 人在场确认或预授权 | 保存决定和责任主体 |
| Settlement / Receipt | Payment result | 关联支付、交付与结算证据 |

### 首个 AP2 场景

只选择一个边界明确的 B2B 场景，例如：

> 企业预先授权研究 Agent 在 7 天内、总额 50 美元以内，从白名单数据商购买指定类别的数据查询。

### 验收标准

- AP2 凭证可以导入并映射为 BU2 内部对象。
- BU2 策略仍可进一步收窄 AP2 授权。
- AP2 授权不能突破工作区硬预算和冻结状态。
- 凭证失效、撤销或内容不匹配时拒绝交易。
- 审计页同时显示外部 Mandate 和 BU2 内部判断。

### 禁止扩展线

- 不一次实现所有 AP2 示例场景。
- 不建设电商搜索、购物车或推荐系统。
- 不承担发卡、收单或清算角色。
- 不因为 AP2 支持多支付方式，就同时接入所有支付通道。
- 不把 AP2 当作 BU2 权限系统的替代品。

## 7. P4：多支付通道编排

只有以下条件同时成立才进入：

- 客户明确需要至少两种支付方式。
- 单一通道已经形成稳定交易量。
- 商户覆盖或结算需求无法由现有通道满足。
- 团队具备支付运维和合规能力。

可选通道按客户需求逐一评估：稳定币、虚拟卡、企业预付余额或持牌支付服务商。

每增加一个通道必须证明：

- 带来明确客户或交易量。
- 不改变 BU2 核心对象。
- 可以复用现有策略和审计链。
- 失败、退款和对账边界已经定义。

## 8. 防止协议反向扩大 MVP 的机制

### 8.1 稳定核心对象

MVP 只围绕以下对象验收：

- Agent Identity
- Wallet
- Payment Mandate
- Quote
- Payment Intent
- Authorization
- Transaction
- Delivery Evidence
- Settlement
- Receipt

任何协议特有对象必须作为扩展字段或适配器对象，不能侵入核心模型。

### 8.2 每阶段一个协议场景

一个阶段只验证一个端到端场景。禁止用“协议支持”替代产品结果。

错误目标：

> 支持 x402、AP2 和三条链。

正确目标：

> 研究 Agent 在 0.10 美元上限内完成一次数据购买，且没有重复支付并留下完整证据。

### 8.3 功能进入清单

协议衍生功能必须同时满足：

1. 至少 3 个目标客户提出同类需求。
2. 无法由现有核心对象表达。
3. 有明确的端到端验收标准。
4. 不要求 BU2 承担新的资金角色。
5. 不降低预算、策略或审计完整性。

缺少任何一项则不进入当前版本。

### 8.4 协议适配器契约

所有适配器只能实现：

```text
prepare(request)
execute(authorization)
confirm(external_result)
reverse(transaction)
health()
```

适配器不能：

- 修改预算
- 修改策略
- 自行批准申请
- 创建没有任务归属的交易
- 覆盖历史账本

### 8.5 双重路线图

产品路线图和协议路线图分开管理：

- 产品路线图衡量客户价值、使用和付费。
- 协议路线图衡量互操作、执行和可靠性。

只有产品门槛通过，协议路线图才能前进。

## 9. 阶段决策表

| 阶段 | x402 | AP2 | 真实资金 | 主要验证 |
| --- | --- | --- | --- | --- |
| P0 MVP | 模拟 | 仅概念映射 | 否 | 预算治理是否值得付费 |
| P1 沙盒 | 单场景 | 不接入 | 测试资产 | 支付与交付证据闭环 |
| P2 生产验证 | 白名单小额 | 不接入 | 非托管小额 | 支付治理商业价值 |
| P3 企业授权 | 可作为支付扩展 | 单一 B2B 场景 | 受控 | 跨平台授权与责任证明 |
| P4 编排 | 多商户 | 多场景 | 多通道 | 规模化互操作 |

## 10. 当前决策

截至 Product v0.1：

- P0 立即执行。
- P1 只进入技术原型计划，不进入首版承诺。
- P2 必须等待客户与合规门槛。
- P3 不进入 MVP 排期，只保留对象映射设计。
- P4 作为远期方向，不估算开发日期。
