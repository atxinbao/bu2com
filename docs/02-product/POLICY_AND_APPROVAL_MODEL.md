# BU2 预算与审批模型 v0.1

## 1. 目标

将模糊的自然语言意图转换为可计算、可解释和可审计的消费权限。

策略引擎必须是确定性的：在策略版本和输入相同时，输出必须相同。

## 2. 授权层级

```text
Workspace Policy
        ↓
Project Policy
        ↓
Agent Policy
        ↓
Task-specific Grant
```

下层只能收窄上层权限，不能突破上层硬限制。

## 3. 支出申请契约

```json
{
  "workspace_id": "ws_123",
  "project_id": "proj_research",
  "agent_id": "agent_analyst",
  "task_id": "task_456",
  "merchant": "example-data-provider",
  "category": "market_data",
  "item": "company_profile_query",
  "amount_minor": 80,
  "currency": "USD",
  "purpose": "完成公司行业地位分析",
  "expires_at": "2026-09-01T12:00:00Z",
  "idempotency_key": "task_456-data-01"
}
```

`purpose` 可以由模型生成，但金额、币种、商户和商品必须作为结构化字段独立校验。

## 4. 策略条件

MVP 支持：

- 金额：单笔、任务、每日、每月
- 作用域：工作区、项目、Agent
- 商户：白名单、黑名单
- 类别：模型、搜索、数据、算力、SaaS
- 环境：开发、测试、生产
- 时间：生效期、有效时段
- 任务：是否存在、是否活跃
- 审批：金额或类别触发人工审批

## 5. 判断结果

### APPROVED

申请符合全部硬规则，并且不需要人工审批。

返回：授权 ID、批准金额、有效期、策略版本和剩余额度。

### REVIEW_REQUIRED

申请未违反硬规则，但命中人工审批条件。

返回：审批 ID、触发原因、审批人和到期时间。

### DENIED

申请违反硬规则或缺少必要上下文。

返回：拒绝代码、命中规则和可修正字段；不能只返回模型生成的解释。

## 6. 规则优先级

1. 工作区冻结或 Agent 停用
2. 凭证有效性
3. 数据完整性与幂等性
4. 预算硬上限
5. 商户和类别限制
6. 时间和环境限制
7. 人工审批条件
8. 自动批准

任何前置拒绝都不能被后续规则覆盖。

## 7. 示例

### 示例 A：自动批准

```text
申请：指定搜索 API，$0.03
规则：白名单商户；单笔上限 $0.50；每日余额充足
结果：APPROVED
```

### 示例 B：需要审批

```text
申请：行业数据库报告，$12
规则：单笔超过 $5 需要人工审批；任务预算仍充足
结果：REVIEW_REQUIRED
```

### 示例 C：直接拒绝

```text
申请：未知地址转账，$1
规则：仅允许白名单服务商；禁止通用转账
结果：DENIED
```

## 8. 审批上下文

审批人至少看到：

- Agent 和负责人
- 项目与任务目标
- 商户、商品、金额和币种
- Agent 提交的购买理由
- 当前预算和已用金额
- 命中的审批规则
- 相似历史申请
- 申请有效期

审批动作必须记录审批人、决定、原因和时间。

## 9. 版本与重放

- 每次策略修改产生新版本
- 支出申请保存判断时使用的策略版本
- 历史交易不随新策略重新解释
- 管理员可以使用历史输入重放策略，比较新旧结果
- 紧急冻结立即影响所有尚未执行的授权

## 10. 钱包阶段的产品边界

进入真实支付阶段后仍坚持：

- BU2 不把私钥交给大模型
- 模型输出不能直接成为支付指令
- 支付授权与外部内容解析隔离
- 非托管执行失败不能记为成功支出
- 退款和冲正通过新账本事件记录
