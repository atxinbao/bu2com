    BU2 系统架构宪法

    版本：1.0
    生效日期：2026-09-01
    制定者：Codex
    适用范围：BU2.com 产品、API、SDK、MCP、Worker、支付适配器、账本、数据平台及其后续替代系统

    序言

    BU2.com 是 Agent 的 AI 收付平台。系统的长期目标不是让同一套代码、语言、数据库或云平台运行一百年，而是保证：

    即使团队、技术栈、支付协议、密码算法、监管环境和基础设施全部变化，BU2 保存的身份、授权、交易、交付、结算和凭证事实仍然可解释、可验证、可迁移、可恢复并可继续处理。

    本文件定义 BU2 架构中长期不可轻易破坏的原则。具体实现可以替换，核心业务事实和一致性规则不得因技术迁移而丢失。

    文中的规范词具有以下含义：

    • 必须：任何实现都不得违反。
    • 应当：默认遵循；偏离时必须通过架构决策记录说明理由。
    • 可以：根据阶段和实际需求选择。

    第一章：稳定的业务事实

    第一条：系统必须回答的长期问题

    每笔交易必须能够回答：

    1. 谁发起了交易；
    2. Agent 代表哪个账户或主体；
    3. 依据什么授权；
    4. 向谁购买了什么商品或服务；
    5. 请求、授权、预留、结算和退款分别是多少；
    6. 是否完成交付，由谁验收；
    7. 资金通过哪个通道最终到达哪里；
    8. 是否发生失败、退款或争议；
    9. 哪些证据可以独立验证以上事实。

    第二条：稳定核心对象

    BU2 的核心领域对象为：

    Account
AgentIdentity
Credential
PaymentMandate
Quote
PaymentIntent
Authorization
Transaction
DeliveryEvidence
Settlement
Receipt
Refund
Dispute
LedgerEvent

    外部协议、数据库表、API 框架和程序语言不得取代这些领域概念。

    第三条：外部任务只是上下文

    ChatGPT 会话、Codex 任务、Agent Run 或自动化工作流只能通过 external_context_id 等字段关联交易。

    BU2 不得要求用户迁移到 BU2 创建任务，外部任务也不得成为完成支付的强制主数据。

    第二章：Transaction Core

    第四条：交易状态的唯一所有者

    BU2 必须存在唯一的 Transaction Core，负责：

    • Quote 和 PaymentIntent；
    • Authorization；
    • 交易状态机；
    • 资金预留、释放和结算；
    • DeliveryEvidence；
    • Refund 和 Dispute；
    • LedgerEvent；
    • Receipt 数据准备。

    只有 Transaction Core 可以改变 BU2 交易状态。

    支付适配器、Webhook、签名、通知、分析和对账服务只能提交命令、执行结果或证据，不得直接修改核心交易表。

    第五条：强一致核心边界

    以下对象在能够证明分布式拆分必要性以前，应由同一个 Transaction Core 和同一个事务边界管理：

    PaymentIntent
Authorization
Transaction
Settlement
LedgerEvent
Transactional Outbox

    不得为了“微服务数量”拆散资金状态的一致性边界。

    第三章：不可覆盖的历史

    第六条：交易事实只追加，不覆盖

    关键业务事实必须追加写入 LedgerEvent。历史事件不得被更新为另一种含义，也不得通过删除掩盖已发生的行为。

    更正必须使用新事件表达，例如：

    SettlementCompleted
→ SettlementCorrected
→ RefundCompleted

    第七条：当前状态与历史事实双轨保存

    系统应同时维护：

    • 当前状态投影：服务实时查询；
    • 追加式账本：审计、恢复、重建、迁移和对账。

    当前状态必须能够从历史事实中验证；长期目标是能够从 Ledger 重建关键交易投影。

    第八条：事件顺序

    事件顺序不得只依赖时间戳。每个聚合必须包含：

    event_id
ledger_sequence
aggregate_id
aggregate_version
occurred_at
recorded_at

    并发写入必须通过版本检查阻止静默覆盖。

    第四章：交易状态与金额

    第九条：关键状态永久分离

    以下状态在任何版本中都不得合并：

    authorization_required
authorized
funds_reserved
delivery_submitted
settled
refunded
disputed

    “获得授权”不等于“已经扣款”，“资金预留”不等于“已经结算”，“已经交付”也不自动等于“验收成功”。

    第十条：金额模型

    所有金额必须使用：

    整数最小货币单位 + ISO 4217 币种

    不得使用二进制浮点数保存资金金额。

    以下金额必须分别保存：

    requested_amount
authorized_amount
reserved_amount
settled_amount
refunded_amount
fee_amount

    必须满足：

    refunded_amount ≤ settled_amount ≤ reserved_amount ≤ authorized_amount

    第十一条：数据库约束

    关键业务约束必须同时存在于领域代码和数据库中。至少包括：

    UNIQUE(account_id, endpoint, idempotency_key)
UNIQUE(provider, provider_reference)
UNIQUE(transaction_id, settlement_kind)
CHECK(refunded_amount <= settled_amount)
CHECK(settled_amount <= reserved_amount)

    第五章：幂等、异步与故障恢复

    第十二条：资金操作必须幂等

    每个可能影响资金的操作必须贯穿三层幂等：

    BU2 API Idempotency-Key
BU2 Adapter Operation ID
Payment Provider Idempotency-Key

    相同幂等键和相同载荷必须返回原结果；相同键配合不同载荷必须拒绝。

    第十三条：不得依赖分布式强事务

    服务之间必须采用：

    本地数据库事务
+ Transactional Outbox
+ 幂等消费者
+ Saga / 补偿操作
+ 主动对账

    不得要求多个服务数据库同时提交才能保证一笔交易成立。

    第十四条：超时不是失败证明

    支付通道请求超时后，交易不得直接标记为失败。系统必须进入可恢复的未知状态，例如：

    provider_unknown

    随后通过通道查询、Webhook 或对账确认真实结果。

    第十五条：系统必须能够失败后恢复

    每个资金操作必须具备：

    • 查询通道当前状态；
    • 安全重试；
    • 幂等恢复；
    • 人工接管；
    • 自动对账；
    • 补偿或冲正路径。

    稳定性的定义不是“永不失败”，而是失败后能够确定发生了什么，并安全恢复。

    第六章：协议与支付通道边界

    第十六条：核心领域独立于协议

    x402、AP2、银行卡、稳定币、银行转账及未来协议只能通过 Adapter 接入。

    BU2 Transaction Core
        ↓
Payment Adapter Interface
        ├── Simulated Adapter
        ├── x402 Adapter
        ├── Card Adapter
        ├── Stablecoin Adapter
        └── Bank Adapter

    任何外部协议不得重新定义 BU2 的核心状态。

    第十七条：Adapter 的职责边界

    Adapter 可以：

    • 执行授权、预留、结算、释放、退款和查询；
    • 保存通道引用和通道原始结果；
    • 将通道状态映射为标准结果。

    Adapter 不可以：

    • 直接修改 Transaction Core 数据库；
    • 把通道“成功响应”直接当作 BU2 结算事实；
    • 绕过 PaymentMandate；
    • 绕过幂等、交付和对账规则。

    第七章：身份与密码学

    第十八条：业务身份不得绑定单一平台

    BU2 使用稳定的内部 Account ID 和 AgentIdentity ID。OpenAI、Google、OAuth、API Key、DID、证书或钱包地址只能作为可替换 Credential。

    外部平台变化时，可以替换 Credential，但不得改变历史交易中的 Account 和 AgentIdentity。

    第十九条：密码算法必须可迁移

    Receipt 必须保存：

    schema_version
canonicalization_version
signature_algorithm
verification_key_id
signed_at
signature

    私钥必须由 KMS/HSM 或等效隔离签名设施管理。应用代码不得持有生产私钥明文。

    系统必须支持：

    • 密钥轮换；
    • 多算法并行；
    • 旧凭证长期验证；
    • 撤销记录；
    • 历史公钥归档；
    • 必要时生成新算法迁移证明。

    第八章：开放契约与版本治理

    第二十条：所有公共边界必须版本化

    以下内容必须独立版本化：

    API
Event Schema
Receipt Schema
PaymentMandate
Policy
Adapter
Database Migration
Signature Key
Canonicalization Rules

    第二十一条：事件兼容性

    已发布事件：

    • 可以增加可选字段；
    • 不得改变既有字段含义；
    • 不得重新使用废止字段名；
    • 不得让同一事件名称表达不同事实。

    不兼容变化必须使用新事件名称或新主版本。

    第二十二条：契约优先

    OpenAPI、JSON Schema、MCP Schema、SDK 类型和事件 Schema 必须来源于同一逻辑契约，防止各端各自解释交易含义。

    TypeScript 类型只负责开发期检查，外部输入仍必须执行运行时验证。

    第九章：数据主权、迁移和生命周期

    第二十三条：数据必须可以离开当前技术栈

    BU2 的关键数据不得只能通过当前代码、云厂商或数据库产品解释。

    系统必须能够导出类似以下长期归档包：

    manifest.json
accounts.ndjson
agent-identities.ndjson
transactions.ndjson
ledger-events.ndjson
receipts.ndjson
public-keys.json
schemas/
checksums.txt

    归档包应具备校验和和签名。

    第二十四条：交易事实与个人数据分离

    长期保留的交易事实应与可删除或有期限保留的个人数据分离。

    完整 Prompt、私人对话、支付密钥、银行卡明文和钱包私钥不得进入核心账本。

    第二十五条：恢复必须定期演练

    备份存在不等于可以恢复。系统必须定期验证：

    • 全新环境数据库恢复；
    • Ledger 重建当前状态；
    • Receipt 独立验证；
    • 数据跨数据库导出和导入；
    • 签名密钥轮换；
    • Adapter 替换；
    • 旧事件被新消费者读取。

    第十章：服务边界和演进

    第二十六条：先模块化，再按故障边界拆分

    早期采用模块化 TypeScript 平台和独立 Worker：

    apps/
├── console-web
├── payment-api
├── webhook-worker
├── adapter-worker
└── reconciliation-worker

packages/
├── domain
├── contracts
├── ledger
├── receipt
├── observability
└── adapters

    只有出现以下证据时才拆成独立微服务：

    • 需要独立扩容；
    • 需要不同权限或密钥边界；
    • 故障必须隔离；
    • 发布节奏明显不同；
    • 已有独立维护团队；
    • 当前架构存在经过测量的瓶颈。

    第二十七条：推荐拆分顺序

    微服务化应优先拆出：

    1. Webhook Delivery；
    2. Payment Adapter Worker；
    3. Reconciliation；
    4. Receipt Signing；
    5. Identity/Credential；
    6. 最后评估是否需要拆分 Transaction Core。

    第二十八条：数据库所有权

    成熟微服务可以拥有独立数据库，但任何服务不得绕过 API 或事件契约直接修改另一个服务的数据。

    PaymentIntent、Transaction、Settlement 和 Ledger 应长期由 Transaction Core 统一持有，除非新的设计能够证明不会破坏资金一致性。

    第十一章：运营稳定性

    第二十九条：系统必须具备的运行机制

    所有生产服务必须具备：

    • 健康检查与就绪检查；
    • 多实例与自动恢复；
    • 明确超时；
    • 有条件重试和指数退避；
    • 熔断；
    • 限流和背压；
    • 死信队列；
    • 优雅停机；
    • 滚动或灰度发布；
    • 数据库连接池和容量边界。

    第三十条：可观测性

    每笔操作必须贯穿：

    trace_id
request_id
account_id
agent_id
payment_intent_id
transaction_id
event_id
provider_reference

    监控必须覆盖：

    • 技术指标：延迟、错误率、资源和队列；
    • 交易指标：授权、预留、结算、退款和争议；
    • 一致性指标：账本与通道差异、未知状态和重复引用；
    • 运营指标：Webhook 死信、人工对账、Adapter 熔断和密钥状态。

    第三十一条：对账是核心能力

    系统必须持续比较：

    BU2 Ledger
↕
支付提供商账单
↕
银行、卡组织或链上实际记录

    任何无法自动解释的差异必须进入可追踪的人工处理状态。

    第十二章：发布、测试和质量门槛

    第三十二条：环境隔离

    Development、Sandbox 和 Production 必须使用独立的：

    • 数据库；
    • 凭证；
    • 签名密钥；
    • Webhook Secret；
    • 支付通道账户；
    • 域名；
    • 监控和告警。

    第三十三条：发布顺序

    生产变化应经过：

    单元测试
→ 状态机与契约测试
→ Sandbox 端到端测试
→ 数据库迁移检查
→ 小流量 Canary
→ 逐步扩大
→ 可验证回滚

    第三十四条：永久回归用例

    以下测试不得删除：

    • 重复请求不会重复扣款；
    • 相同幂等键配合不同载荷必须拒绝；
    • 未授权不能预留资金；
    • 未交付不能结算；
    • 退款不得超过结算金额；
    • 并发结算只能成功一次；
    • 服务重启后交易和幂等记录仍可恢复；
    • Webhook 可以重复投递但接收结果不重复；
    • Receipt 可以脱离主系统验证；
    • Ledger 可以重建关键状态。

    第十三章：架构治理

    第三十五条：架构决策记录

    所有影响以下内容的决定必须建立 ADR：

    • 核心领域对象；
    • 资金状态机；
    • 数据所有权；
    • 公共 API 或事件；
    • 支付 Adapter；
    • 密钥和签名；
    • 数据保留和迁移；
    • 服务拆分或合并。

    ADR 必须记录问题、候选方案、选择理由、后果和重新评估条件。

    第三十六条：宪法修改程序

    修改本宪法必须：

    1. 创建独立 ADR；
    2. 说明原条款无法继续满足的事实；
    3. 分析交易一致性、历史兼容、数据迁移和 Receipt 验证影响；
    4. 提供旧数据和旧客户端迁移方案；
    5. 通过架构负责人和交易领域负责人评审；
    6. 提升宪法版本并保留旧版本。

    任何紧急修改不得覆盖或删除既有交易事实。

    架构宪法十项最高原则

    1. 交易事实只追加，不覆盖。
    2. 只有 Transaction Core 可以改变交易状态。
    3. 授权、预留、交付、结算和退款永远是不同事实。
    4. 所有资金操作必须端到端幂等。
    5. 外部协议和支付通道只能通过 Adapter 接入。
    6. Receipt 必须能够脱离 BU2 独立验证。
    7. 业务身份不得绑定任何单一平台或凭证。
    8. API、事件、策略、凭证、密钥和迁移必须版本化。
    9. 任何当前技术组件都必须可以被替换和迁移。
    10. 每次故障后必须能够根据历史事实确定状态并安全恢复。

    当前推荐参考架构

    Web Console / REST / SDK / MCP / AP2
                   ↓
              API Gateway
                   ↓
            Transaction Core
                   ↓
              PostgreSQL
     Current State + Ledger + Outbox
                   ↓
             Message Broker
      ┌────────────┼─────────────┐
      ↓            ↓             ↓
Payment Adapter  Receipt       Webhook
Worker           Signing       Delivery
      ↓            ↓             ↓
支付通道         KMS/HSM       客户系统
                   ↓
          Reconciliation Service

    当前实现可以使用 TypeScript、React、PostgreSQL 和托管消息队列。技术选择可以演进，但必须遵守本宪法定义的业务事实、一致性和可迁移原则。

    最终声明

    BU2 不追求一套永远不变的代码，而追求一套可以不断被安全替换的系统。

    能持续一百年的不是 TypeScript、PostgreSQL、云平台或微服务，而是：

    稳定的领域模型、不可覆盖的交易事实、开放且版本化的契约、可独立验证的 Receipt，以及持续迁移、对账、恢复和重建的能力。
